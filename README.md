# SSH Log Analyzer

A small Python tool that reads an OpenSSH authentication log and flags **brute-force attacks** and **possible account takeovers**. I built it as a learning project for SOC / blue-team work and tested it on logs from my own virtual lab.

Standard library only, no installation needed.

## What it detects

| Alert | Severity | MITRE ATT&CK | Rule |
|---|---|---|---|
| Suspicious activity (brute force) | MEDIUM | T1110.001 Password Guessing | at least `--threshold` failed passwords from one IP within `--window` seconds |
| Possible compromise | HIGH | T1078 Valid Accounts | a successful login from an IP that made at least `--threshold` failed attempts within the `--window` seconds just before the login |

The report also lists the most targeted usernames (including accounts that do not exist), sorted from most to least attacked, and a suggested `ufw deny` command for each alert. The commands are only written to the report; the tool never runs them.

IPv4 and IPv6 addresses are supported.

## Quick start

```bash
python3 analyze.py sample_logs/auth_lab_synthetic.log
```

```
=== SSH ANALYSIS SUMMARY ===
Analyzed file: sample_logs/auth_lab_synthetic.log
Detected possible breaches [HIGH]: 1
Suspicious IP addresses (Brute Force) [MEDIUM]: 2
Full report saved to: report.json
```

A full JSON report is in [`examples/example_report.json`](examples/example_report.json). The takeover entry looks like this (`attempts` is the number of failed attempts inside the window before the login):

```json
{
    "severity": "HIGH",
    "type": "POSSIBLE COMPROMISE",
    "mitre": "T1078 - Valid Accounts",
    "ip": "192.168.100.20",
    "user": "kamil",
    "attempts": 47,
    "recommended_action": "sudo ufw deny from 192.168.100.20"
}
```

### Options

| Option | Default | Meaning |
|---|---|---|
| `logfile` | required | path to the log file (syslog format, e.g. `/var/log/auth.log`) |
| `--threshold` | 5 | failed attempts that trigger an alert |
| `--window` | 60 | sliding time window in seconds |
| `--year` | current year | syslog timestamps have no year, so it is added here |
| `--output` | `report.json` | where to write the report |

## The lab

Everything was run on my own virtual machines in VirtualBox: an **Ubuntu Server** with OpenSSH and a **Kali Linux** machine. I attacked a user account on the SSH service with **Hydra** and analysed the server's authentication log.

## Sample data

| File | Origin |
|---|---|
| `sample_logs/auth_lab_real.log` | **Real log** (29 lines) from the Ubuntu Server VM, recorded during a Hydra attack from the Kali VM in November 2026. |
| `sample_logs/auth_lab_synthetic.log` | **Synthetic log** (863 lines) generated by a script, **not captured from a real system**. It copies the Ubuntu 24.04 format and mixes legitimate logins, typos, a fast brute force that ends in a takeover, a scan with many usernames, a slow attack and IPv6 noise. Used for development and demos. |

The real log is short: it contains only 6 failed attempts, and Hydra found the password after 4 failures. With the default threshold of 5 the tool reports the brute force but not the takeover. Lower the threshold to see both:

```bash
python3 analyze.py sample_logs/auth_lab_real.log --threshold 3
```

## How it works

1. Only `Failed password` and `Accepted password` lines are used; every other line is ignored.
2. For each IP the tool keeps the timestamps of its failed attempts from the last `--window` seconds. When their number reaches the threshold, the IP is reported as brute force.
3. When an IP logs in successfully, the tool counts its failed attempts from the last `--window` seconds. If there are at least `--threshold` of them, the login is reported as a possible compromise.

Hydra checks a password by really logging in, so the correct guess shows up as a successful login right after the failed ones. That is the case the takeover rule is built for.

## Limitations

- **A takeover is reported only if the successful login comes within the time window** after the failed attempts. A slow or throttled attack, or a login from a different IP address, is missed.
- **Slow attacks are missed.** In the synthetic log, `203.0.113.50` made 14 attempts over about 2.5 hours, but never 5 inside one minute.
- **The threshold must not be higher than the number of failures before the correct guess** (see the real log above).
- Every successful login inside the window raises its own alert, so repeated logins right after an attack are reported more than once.
- A normal user who mistypes the password `--threshold` times within the window and then logs in is flagged as well.
- Only password authentication is analysed; public-key and PAM lines are not.
- Syslog has no year, so `--year` is needed for old logs. Logs spanning New Year are not supported, and lines must be in chronological order.
- This is a heuristic helper, not a replacement for fail2ban or a SIEM. Check the suggested `ufw` commands before running them, because they could block your own access.
